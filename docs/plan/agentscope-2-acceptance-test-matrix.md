# AgentScope 2.0 替换验收测试矩阵与故障注入建议

- 状态：测试与验收框架预先建立，待阶段 0 / 阶段 1.5 接入真实接口
- 建立日期：2026 年 9 月 12 日
- 适用计划：[AgentScope 2.0 替换、正式数据库收口与云端 / 本地运行底座计划](./agentscope-2-enterprise-runtime-foundation-plan.md)
- 适用范围：AgentScope 2.0、PostgreSQL 正式状态、本地设备命令 / Outbox / Inbox、迁移、备份恢复和 LangGraph 清理
- 当前限制：本文件不改变业务逻辑，不迁移 SQLite，不替换 LangGraph，也不假设尚未冻结的 Runtime / 数据库 / 设备 API

## 1. 使用原则与证据约定

本矩阵把计划中的“阶段 1.5 最小端到端纵向切片”、第 6.5 节 PostgreSQL 运维硬约束、第 7.3 节本地命令协议、第 7.4 节授权撤销、第 7.5 节资产可恢复性和第 9.1 节证据要求，转换为可执行的验收场景。

所有场景都必须使用隔离的测试企业和可复现数据。每次运行至少记录：

- `org_id`、`principal_id`、`run_id`；
- 涉及本地动作时的 `command_id`、`action_id`、`idempotency_key`、`device_id`、`lease_epoch` / `fencing_token`；
- 涉及迁移时的 `migration_batch_id`、源快照指纹、目标数据库版本和恢复游标；
- 涉及资产时的 `asset_id`、`asset_version_id`、期望 hash、实际 hash 和 locator；
- 注入动作的绝对时间、进程 / 设备实例、请求或事件序号，以及最终状态；
- 测试日志、事件序列、数据库校验结果、审计记录、截图 / 录屏（人工演练适用）和结论签署。

默认证据目录为：

```text
artifacts/acceptance/<release-or-build>/<acceptance-id>/<attempt>/
├── input.json                 # 脱敏测试输入和版本
├── identifiers.json           # org / run / command / asset / batch ID
├── timeline.jsonl             # 注入、重试、状态变化的有序时间线
├── events.jsonl               # QAgent 正式事件或导出的等价记录
├── db-checks/                 # 数量、主键、外键、权限、版本、hash 校验
├── logs/                      # 服务、设备、迁移、备份恢复日志
└── verdict.md                 # 放行 / 阻断结论、异常和责任人
```

正式环境不得把真实密钥、长期 token、文件原件或未脱敏企业数据写入上述证据目录。若客户环境已有发布证据库，以客户证据库为最终保存位置，但仍须保留上述字段和可追溯关联。

### 1.1 状态与幂等的共同判定

- 事件和状态必须能按正式记录重建；进程内存、AgentScope 私有 checkpoint、本地缓存或日志不能作为唯一依据。
- 同一逻辑本地动作使用同一 `command_id` / `idempotency_key` 重投；重新发起一个逻辑动作必须使用新身份并记录原因。
- 重复 ACK、重复完成回执和乱序回执只能合并为一次有效状态变化；冲突或过期回执要被拒绝 / 记录，不得倒退终态或创建第二次副作用。
- 取消与完成竞态按实际副作用和可中断性判定：未开始可取消，已开始且可中断则停止并回 `CANCELLED`，不可安全回滚则进入 `MANUAL_RECONCILIATION`，不能靠“没有收到回执”自动重试。
- 任何未知运行中任务、未知来源资产、未解释迁移差异、重复副作用或越权成功都是阻断放行的 P0。

| AS2-RT-001 | 一个隔离 `org_id`、同一 `run_id` 的执行中 / 等待审批 / 等待设备回执三种断点，事件序列、恢复点、授权和关联 command 快照 | 重启前后 Run / event / recovery-point 快照差异；服务退出信号、启动恢复日志、worker lease；重复执行计数；缺失事件或未知 in-flight Run 清单 |

| AS2-DEV-002 | 固定 `command_id` / `idempotency_key`；N 次重复投递样本；覆盖未回执、执行中、已成功三个阶段的可计数测试副作用处理器 | 每次投递的消息 ID、处理器调用计数、执行账本唯一性冲突、事务 / compare-and-set 结果、是否创建第二个输出或外部调用 |
| AS2-DEV-003 | 同一 command 的 ACK、完成、旧版本、终态后回执和冲突结果摘要样本；事件版本 / 序号基线 | 回执原文脱敏副本、版本 / 序号比较结果、状态变更前后快照、被拒绝或进入异常的原因码、事件和完成计数差异 |

| AS2-AUTH-001 | 两个权限不同的 principal、可撤销授权 / lease / fencing；未开始命令、长任务检查点和待写完成回执 | 判权输入与授权版本、撤权传播时间、旧 token / fencing 写入结果、拒绝原因、停止检查点、是否出现越权成功或旧 attempt 写成功 |

| AS2-ASSET-002 | 固定内容和期望 SHA-256；校验前原子替换内容、缓存失效和重连场景；新版本候选 | 期望 / 实际 hash、文件大小 / mtime（如适用）、校验阶段和读取节点、拒绝事件、旧 / 新 `asset_version_id` 关系、是否发生错误版本副作用 |
| AS2-MIG-001 | 固定 source snapshot、版本化 migration、`migration_batch_id`、正常记录和可定位坏记录；提交前后中断点；源 / 目标对账基线 | migration ledger、批次状态和恢复游标、已提交 / 未提交 / 隔离记录、重跑前后计数、主外键 / org / 权限 / 版本 / hash 差异报告 |
| AS2-DB-001 | 与正式版本匹配的隔离 PostgreSQL；可校验备份 / WAL 或 PITR 材料；包含 Run、command、权限、资产引用和审计的基线数据 | 备份校验结果、恢复时间点、RPO / RTO 计时、恢复前后 counts / checksums、数据库版本、核心 SQL / smoke API、缺失对象和权限差异 |
| AS2-CLEAN-001 | 生产代码、部署配置、依赖 / lockfile、镜像 SBOM、启动日志、进程清单、主链回归样本；批准的历史文档豁免清单 | 静态命中路径、依赖树和镜像层、启动 / 网络调用、运行期 import、checkpoint / run 写入来源、豁免项及批准关联；任一未批准残留都阻断放行 |

失败诊断至少要能回答：失败发生在哪个状态 / 事务边界、哪个身份或版本参与、是否产生真实副作用、能否安全重试、需要自动恢复还是人工处置，以及对应的责任人和证据路径。

## 3. 场景数据与最小纵向切片

阶段 1.5 应选择一个既有会话 / Goal / 工具动作作为共同样本，不另造业务功能。建议最小数据集如下：

| 数据集 | 内容 | 用途 | 约束 |
| --- | --- | --- | --- |
| `org-basic` | 一个测试企业、两个有不同权限的 principal、一个可撤销委派 | 重启、权限撤销、跨设备一致性 | 不使用开发机现有账号；权限变更有版本 / 时间戳 |
| `run-basic` | 一个固定输入快照、一个 Agent / App revision、执行中 / 等待中 / 终态事件样本 | Run 恢复、取消竞态、LangGraph 清理后的主链回归 | 固定业务 Run ID；保存输入摘要而非密钥 |
| `device-basic` | 一台虚拟或测试设备、能力白名单、lease / fencing 初始值、可重置 Inbox / Outbox | 离线重连、重复投递、重复回执、撤权 | 副作用处理器只写测试账本；禁止访问真实邮件、文件删除或桌面系统 |
| `asset-basic` | 一个固定内容文件、不可变版本、期望 SHA-256、受控 locator | 不可用、hash 漂移、结果引用 | 原件放隔离临时目录 / 测试存储；测试完成可清理但元数据证据保留 |
| `migration-basic` | 含正常记录、关系、权限和一条坏记录的源快照 | 中断续跑、重复批次和对账 | 记录源快照指纹；坏记录不得通过“人工直接改库”掩盖 |
| `backup-basic` | 覆盖身份、Agent / App、Run、command、资产元数据、审计的 PostgreSQL 数据集 | 备份恢复和 RPO / RTO | 与目标 schema / migration 版本绑定；恢复到隔离实例 |

测试数据生成可先使用仓库内 `backend/tests/acceptance/test_data.py` 的确定性 ID 生成器。它只生成 `org_id`、`run_id`、`command_id`、`idempotency_key`、资产 / 批次 ID 和证据目录，不创建数据库行，也不模拟未来接口。

## 4. 故障注入建议

故障注入必须是可重复、可停止、可审计的测试操作。优先在隔离环境使用注入适配器，不在生产直接 kill、删库或篡改真实资产。每种注入都要同时验证“系统拒绝错误继续”和“恢复后可以继续 / 人工处置”。

| 故障类别 | 未来建议的模拟方式 | 注入时机 / 变体 | 必须观察 | 恢复与清理 |
| --- | --- | --- | --- | --- |
| 数据库短暂不可用 | 测试 PostgreSQL 代理 / sidecar 暂停连接、拒绝连接或注入短暂超时；不要在应用中写永久 mock | Run 写事件、Outbox 入队、回执合并、迁移提交前后；测试单次抖动、连续抖动和连接恢复 | 正式事务不产生半条记录；Outbox / command 不丢；客户端看到可解释重试 / 等待；无重复副作用；告警包含 correlation ID | 恢复连接后按同一业务身份重试；校验事务原子性、事件序列和命令状态；清理代理规则 |
| 服务崩溃和重启 | 测试编排器发送 SIGKILL / 强制终止容器并重新启动；保留卷与日志 | 执行中、等待审批、等待设备回执、事务提交边界；优雅退出与非优雅退出 | 重启扫描 PostgreSQL 恢复点；无两个 worker 持有有效 lease；Run / event 不丢不重；启动日志明确恢复数量 / 异常 | 让恢复流程完成，收集进程和数据库证据；未能安全续跑的 Run 必须进入人工处置 |
| 设备断网 | 可控 device transport 丢包 / 延迟 / 断开，或网络 namespace / 代理规则阻断出站连接 | 下发前、收到命令后、ACK 后、执行中、完成回执前；设备重启后重连 | 云端不假报成功；设备本地 Inbox / Outbox 持久；重连补发顺序和去重正确；超时 / 过期可解释 | 恢复网络，等待同步完成；核对 command、回执和副作用计数；清除网络规则 |
| 消息重复投递 | Outbox / message broker 测试适配器按相同消息 ID 重放、并发重放或改变到达顺序 | 同一 command 的 CREATED / ACK / completion；事件和迁移消息也可重放 | 消费者幂等；唯一约束 / compare-and-set 生效；终态不倒退；重复消息有计数和可检索日志 | 保留重放清单作为证据；确认重放不会产生新副作用；清理测试队列 |
| 回执延迟或重复 | 设备 transport 延迟、复制 ACK / completion、发送旧版本 / 冲突摘要 | ACK 晚于完成、完成晚于取消、终态后再次回执、重复相同回执 | 状态机按版本 / 顺序收敛；冲突进入异常 / 人工处置；不重复执行、不覆盖真实结果 | 按协议重放合法回执，检查终态和审计；清除未完成测试命令 |
| 权限撤销 | 测试 IAM / authorization provider 在 Run / command 存在后撤销成员、审批、设备或委派凭据 | 未开始、等待设备、长任务安全检查点、完成回执写入前；同时测试 token 过期 / lease 变更 | 服务端重新判权而非信任旧 token；设备二次拒绝；旧 fencing token 不能写成功；拒绝原因脱敏可追踪 | 恢复权限仅允许显式重新授权 / 新 attempt；不得自动继续旧的不可逆动作；记录人工结论 |
| 资产丢失或 hash 变化 | 测试 locator 指向的临时文件删除 / 不可访问；在校验前原子替换内容；模拟外部存储返回不同内容 | Run 创建后、执行前、读取中、重启 / 重连后；测试权限撤销与同名替换 | `UNAVAILABLE` / `TOMBSTONED` / `HASH_MISMATCH` 等明确状态；无静默换文件；Run 等待 / 人工处置；实际 hash 进入证据 | 恢复原版本或创建新 `asset_version_id`，重新授权后再执行；清理临时文件，保留元数据和证据 |

### 4.1 故障注入通用要求

1. 每次注入先写入 `fault_injection_id`、触发时间、目标实体和预期结果，再执行故障。
2. 注入器必须有显式的 enable / disable、超时和清理动作；测试失败也要回收网络规则、进程和临时资源。
3. 不把异常捕获后直接改成成功状态；恢复逻辑必须经过正式状态机、事务和授权检查。
4. 对不可证明 exactly-once 的边界，验收“至少一次送达 + 幂等键至多一次副作用 + 可追溯人工处置”，不要把网络语义写成不现实的端到端 exactly once。
5. 故障注入报告必须区分：系统自动恢复、可重试等待、人工处置、阻断性错误；不允许使用“最终看起来正常”替代状态和证据。

## 5. 自动化分层与当前落地状态

本次提交已经落地前两项测试基础设施；没有宣称核心验收已通过，也没有写依赖未来接口的大量假测试。

## 6. 放行门槛

候选版本只有在以下条件全部满足后才能进入正式切换：

1. AS2-RT-001、AS2-DEV-001～003、AS2-RUN-001、AS2-AUTH-001、AS2-ASSET-001～002、AS2-MIG-001 的自动化证据全绿；
2. AS2-DB-001 完成一次可复现的隔离环境备份恢复演练，达到计划目标 RPO ≤ 5 分钟、RTO ≤ 30 分钟；若客户环境不同，差异、风险和批准人写入部署验收单；
3. AS2-CLEAN-001 的生产代码、部署配置、依赖锁文件、镜像和启动 / 主链回归扫描为零未批准残留；
4. 迁移对象数量、主键、外键、企业归属、权限和版本校验 100% 通过，或每个例外都有批准的处置单；
5. 没有未分类的运行中任务、未知来源资产、重复副作用、越权成功或未解释的迁移差异；任一项均阻断放行；
6. 阶段 0 已把角色负责人占位符替换为实际负责人，并完成故障注入和回退 / 人工处置 runbook 评审。

## 7. 后续开发优先满足的 5 项验收

1. **先完成 AS2-RT-001：Run 正式状态、事件和恢复点落 PostgreSQL，并证明服务重启可恢复。** 这是所有后续设备、迁移和 Runtime 替换验收的基础。
2. **完成 AS2-DEV-002 / AS2-DEV-003：同一命令幂等副作用、重复 / 乱序回执收敛。** 没有这项，不应扩大本地执行范围或重试策略。
3. **完成 AS2-AUTH-001：服务端判权、撤权传播、lease / fencing 和长任务安全检查点。** 这项直接决定云端常驻和多设备是否安全。
4. **完成 AS2-MIG-001 与 AS2-DB-001：可续跑迁移和备份恢复。** 正式数据库成为唯一来源前，必须能解释中断、差异和恢复时间。
5. **完成 AS2-CLEAN-001：AgentScope-only 主链与 LangGraph 清理门。** 只有在最小纵向切片、恢复、设备和资产链路都通过后，才删除旧 Runtime / 旧正式写入路径。
