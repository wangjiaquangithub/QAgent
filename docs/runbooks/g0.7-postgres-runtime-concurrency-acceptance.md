## 0. 本次验收的定位

本卡是**验收卡，不是功能开发卡**。目标是：在真实 PostgreSQL 上，用至少两个独立数据库连接，验证既有 QAgent Runtime 的 Run / Approval / Runtime Event / execution claim / execution epoch 的事务与并发语义。

明确不做的事：

- 不重构 Runtime 业务代码（`backend/app/qagent_runtime/` 未被修改）；
- 不新增前端页面、不删除 LangGraph、不做顺手重构；
- 不把 SQLite 单测结果当作 PostgreSQL 并发结论；
- 不用「新建空库能跑通」冒充「历史数据迁移成功」。

## 2. 发现并修复的两个真实缺陷

两个缺陷都在真实 PostgreSQL 上稳定复现，且都已获用户明确授权后修复。修复范围为允许写入的 `backend/migrations/`（迁移层）。

### 缺陷 1：0004 迁移在 PostgreSQL 上必然失败（`DependentObjectsStillExist`）

**现象**

```text
psycopg.errors.DependentObjectsStillExist: cannot drop constraint qagent_runs_pkey
on table qagent_runs because other objects depend on it
DETAIL: constraint qagent_run_events_run_id_fkey on table qagent_run_events depends on ...
        constraint qagent_approvals_run_id_fkey on table qagent_approvals depends on ...
        constraint qagent_recovery_points_run_id_fkey on table qagent_recovery_points depends on ...
        constraint qagent_run_assets_run_id_fkey on table qagent_run_assets depends on ...
[SQL: ALTER TABLE qagent_runs DROP CONSTRAINT qagent_runs_pkey]
```

**根因**：`op.batch_alter_table("qagent_runs", recreate="always")` 会强制整表重建，重建时先 DROP 主键，而 4 张子表的外键正依赖该主键。

**与既有文档一致**：该失败与 `docs/plan/agentscope-2-postgres-foundation-runbook.md` §13.3 记录完全一致。

**修复**：改为原地 DDL，不再重建表：

```python
op.drop_constraint("uq_qagent_runs_idempotency_key", "qagent_runs", type_="unique")
op.create_unique_constraint(
    "uq_qagent_runs_org_idempotency_key", "qagent_runs", ["org_id", "idempotency_key"]
)
```

修复后主键 `qagent_runs_pkey` 与 4 张子表外键均保持不变。

### 缺陷 2：`alembic_version.version_num` 宽度不足（35 字符放不进 VARCHAR(32)）

**现象**（缺陷 1 修好后暴露）

```text
psycopg.errors.StringDataRightTruncation: value too long for type character varying(32)
[SQL: UPDATE alembic_version SET version_num='0004_qagent_runtime_org_idempotency' ...]
```

**根因**：Alembic 在 `DefaultImpl.version_table_impl` 中把 `version_num` 硬编码为 `VARCHAR(32)`，但本仓库的 revision id 长度为 35：

| revision | 长度 |
| --- | --- |
| `0004_qagent_runtime_org_idempotency` | 35 |
| `0005_qagent_runtime_execution_claim` | 35 |

**影响面**：这意味着在 PostgreSQL 上，这条迁移链**从未能推进到 0003 之后**。0005（`execution_claim` / `execution_epoch`）因此从未在 PostgreSQL 上真实创建过，直接阻塞本卡的场景 3 / 4 / 5。

**修复尝试**：Alembic 1.20 不支持 `version_num_length` / `version_table_column_type` 这类参数（已在 site-packages 中确认 `version_table_impl` 无长度配置项），因此改为在 `context.configure()` **之前**预建加宽版本表：

```python
VERSION_TABLE = "alembic_version"
VERSION_NUM_LENGTH = 255

def _ensure_version_table_width(connection) -> None:
    table = Table(
        VERSION_TABLE,
        MetaData(),
        Column("version_num", String(VERSION_NUM_LENGTH), nullable=False),
        PrimaryKeyConstraint("version_num", name=f"{VERSION_TABLE}_pkc"),
    )
    table.create(bind=connection, checkfirst=True)
```

`run_migrations_online()` 中先 `_ensure_version_table_width(connection)` + `commit()`，再 `context.configure(...)`。因为 `create(checkfirst=True)` 在表已存在时跳过，Alembic 会直接复用这张 255 宽的表。

**修复后验证**：`upgrade head` 全程通过并停在 `0005 (head)`；`downgrade` 0005→0004→0003→0002 全部成功；重新 `upgrade head` 成功；重复 `upgrade head` 为安全 no-op。

`alembic history`：

```text
<base> -> 0001_postgres_foundation
0001_postgres_foundation -> 0002_qagent_runtime
0002_qagent_runtime -> 0003_qagent_runtime_org_scoping
0003_qagent_runtime_org_scoping -> 0004_qagent_runtime_org_idempotency
0004_qagent_runtime_org_idempotency -> 0005_qagent_runtime_execution_claim (head)
```

迁移后的 schema 实测：

| 检查 | 实测值 |
| --- | --- |
| `alembic_version.version_num` 宽度 | `255` |
| `qagent_runs` 主键 | `qagent_runs_pkey`（PK） |
| `qagent_runs` 唯一约束 | `uq_qagent_runs_org_idempotency_key`（UNIQUE，`org_id, idempotency_key`） |
| 依赖 `qagent_runs` 的子表外键 | **4** 个（证明重建修复未破坏引用完整性） |
| `execution_claim` | `character varying` |
| `execution_epoch` | `integer` |
| `execution_claimed_at` | `timestamp with time zone` |

### 缺陷 3（观察项，非代码缺陷）：`claim_execution(reclaim=True)` 不校验过期

**现象**：两个连接同时调用 `claim_execution(..., reclaim=True)` 且都获胜，epoch 从 2 跳到 4（各取一次 claim）。15 次重复均为该结果，可稳定复现。

**判断**：这属于**分层设计**而非缺陷。`claim_execution` 把 `reclaim=True` 当作调用方的可信判定；过期策略（`execution_claimed_at` 是否超过 `AGENTSCOPE_EXECUTION_CLAIM_TIMEOUT`，默认 300s）在 `RuntimeService.resume_run` 中、调用之前计算。repository 层只负责行锁与 claim 落库。

**处理**：本卡**不修改 Runtime**。场景 4 改为：顺序回收（权威契约）作断言，并发裸回收作为**观察证据**记录，不写成"必然单赢"的假断言。

## 3. 七个场景与结果

所有场景在真实 PostgreSQL 上运行，涉及并发的场景均使用 2 个独立连接（每个 worker 一个 `pool_size=1, max_overflow=0` 的 engine），并在 `Barrier(2)` 之前用 `pg_backend_pid()` 断言两个后端 PID 确实不同。

| 编号 | 场景 | 并发方式 | 结果 | 关键证据 |
| --- | --- | --- | --- | --- |
| 1 | Grant vs Reject | 两后端 + Barrier | 通过 | 恰好一个决策提交；`(approval, run) = (granted, running)` 或 `(rejected, failed)`；决策事件恰好 1 条；sequence 严格递增唯一 |
| 2 | Cancel vs Grant | 两后端 + Barrier | 通过 | 单赢；实测 Cancel 获胜：`run = cancelled`，`approval` 保持 `requested`（当前语义，按卡片要求显式记录） |
| 3 | 同一 Run 抢占 execution claim | 两后端 + Barrier | 通过 | 恰好一个有效 claim；epoch +1；`run.executing` 恰好 1 条；状态 `running → executing` |
| 4 | 过期 claim 回收 | 顺序断言 + 两后端观察 | 通过 | 存活 claim 拒绝重复；过期后回收成功且 epoch +1，旧 claim 失去写权限；并发裸回收双赢（见缺陷 3） |
| 5 | 陈旧 epoch 写入被拒 | 顺序（claim→老化→回收→旧 claim 写入） | 通过 | 旧 claim 的 `set_result` / `set_error` 均为安全 no-op；新 epoch 正常完成 Run，未被覆盖 |
| 6 | 审批决策事务回滚 | 单连接 + 显式事务注入异常 | 通过 | 注入异常后 Approval / Run / Event 全部回滚，无孤儿事件（`sequence=999` 未残留）；后续正常决策成功 |
| 7 | Event sequence 并发正确性 | 2 并发连接 × 每连接 6 次写事件 | 通过 | 18 条事件；sequence 严格递增、唯一、无缺口（1..N）；游标回放顺序与存储顺序完全一致 |

### 3.1 不变量

以下不变量在所有场景中成立，是放行的核心依据：

1. **单赢**：同一 Run 行的并发状态变更，恰好一个写入者提交（场景 1、2、3）。序列化点是 `decide_approval_atomically` / `_transition` / `claim_execution` 共同持有的 run 行锁（`with_for_update()`），**先锁 run 行、再锁 approval 行**。
2. **状态一致**：Approval 与 Run 不会出现矛盾组合；不存在 `approval=granted / run=failed` 或 `approval=rejected / run=running`。
3. **事件序列**：`(run_id, sequence)` 唯一约束 + 行锁下 `max(sequence)+1`，保证严格递增、唯一、无缺口、可游标回放。
4. **epoch 单调**：`execution_epoch` 每次取 claim 严格 +1，旧 epoch 的写入被拒或安全 no-op。
5. **事务原子**：审批决策的 Approval / Run / Event 写入同生共死，异常注入后无半写、无孤儿事件。

### 3.2 场景 2 的语义结论（需负责人确认）

Cancel 与 Grant 并发时，实测 **Cancel 获胜**，且 **Approval 保持 `requested`**：

```json
{ "approval_status": "requested", "run_status": "cancelled" }
```

这是既有实现的当前语义（Cancel 赢得 run 行锁后，Grant 的 `decide_approval_atomically` 因 `run.status != 'waiting_approval'` 而返回 `changed=False`，为安全 no-op）。按卡片要求，此处**记录而非判定为缺陷**。若产品期望 Cancel 后 Approval 也应转入某个终态，需要单独的产品决策。

### 4.3 顺带修复：`app` 包被 harness 遮蔽（预先存在）

**现象**：仓库自带的 `backend/tests/conftest.py` 按此顺序插入路径：

```python

```

而 `backend/packages/harness/app/` 是一个**同名但无关**的包（只含 `gateway`）。结果 `import app` 解析到 harness 的副本，`import app.qagent_runtime` 抛出**误导性**的 `ModuleNotFoundError: No module named 'app.qagent_runtime'`（实为子包查找失败）。

**遗留建议**：共享 `tests/conftest.py` 的路径顺序值得单独修一次（把 harness 追加而非前插），否则所有依赖 `app.*` 的测试都受影响。这超出本卡范围，故仅记录。
